# PRD: <과제 이름>

> Codex가 README·데이터·담당자 답을 근거로 초안을 쓰고 갱신한다. 범위·우선순위·핵심 방법은 작업자가 정하고, 확인되지 않은 내용은 가정으로 표시한다.
> 담당자에게 보낼 질문은 한 메시지에 하나씩 짧은 자연문으로 만든다. 답하기 어려운 경우에만 그 질문에 대한 선택지를 붙인다.

## 1. 배경과 문제
- 지금 누가, 무엇 때문에 불편한가?
- 지금은 이 일을 어떻게 처리하고 있나? (엑셀, 수작업, 기존 시스템)

## 2. 목표
- 이 결과물로 무엇이 달라져야 하나? (한 문장)
- 성공을 무엇으로 판단하나? (숫자 기준이 있으면 숫자로)

## 3. 사용자
- 주 사용자는 누구이고, 얼마나 자주 쓰나?
- 사용자의 기술 수준은? (화면이 필요한가, 결과 파일이면 충분한가)

## 4. 범위
| 반드시 (Must) | 있으면 좋음 (Should) | 이번엔 안 함 (Won't) |
|---|---|---|
| | | |

## 5. 데이터와 입력
- 입력 데이터의 형식, 크기, 출처는?
- 행 하나는 무엇인가? (웨이퍼 1장, Lot 1개, 측정 1회, 하루치 집계 …)
- 각 열은 언제 기록되나? 판정·결과가 나온 뒤에야 채워지는 열이 있나? (있으면 예측에 쓰면 안 됨)
- 결측값, 이상값, 단위 차이 같은 데이터 품질 문제가 알려진 게 있나? 빈 값은 "0"인가 "측정 안 함"인가?
- 핵심 지표의 정확한 정의(분자·분모·집계 단위)는?

## 5-1. 틀렸을 때의 비용
- 놓치는 것(미탐)과 잘못 경보하는 것(오탐) 중 무엇이 더 비싼가? 대략 몇 배인가?
- 하루에 사람이 확인할 수 있는 건수 같은 처리 한계가 있나?
- 결과를 누가 보고 어떤 행동을 하나? (그 행동에 필요한 형태: 표, 그래프, 목록, 파일)

## 6. 제약
- 반드시 써야 하거나 쓰면 안 되는 기술이 있나?
- 보안, 개인정보, 성능(응답 시간, 데이터 양) 요구는?

## 7. 완료 기준 (Acceptance)
- [ ] 사용자가 <행동>하면 <결과>가 보인다
- [ ] <엣지 케이스>에서 <기대 동작>
- [ ] 테스트: `<명령>` 통과
